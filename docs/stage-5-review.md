# Этап 5: восстановление из JSON

SQLite удалён. ZIP и GitHub пока не реализуются.

## Файлы и запуск

`working_directory` задаёт каталог запуска (например `runs/experiment_1`).

```text
runs/experiment_1/
├── .checkpoint.lock
├── run.log
├── first/
│   ├── tree.json
│   ├── progress.json
│   └── first_sol.txt
└── second/
    ├── tree.json
    ├── progress.json
    └── second_sol.txt
```

```sh
./build/graph_downsizing run --config config.local.json
./build/graph_downsizing resume --checkpoint runs/experiment_1 --config config.local.json
```

Основной вариант конфигурации:

```json
{
  "input_directory": "graphs",
  "working_directory": "runs/experiment_1",
  "alpha_step": 0.1,
  "threads": 32
}
```

Пути разрешаются относительно конфигурационного файла. Берём обычные `.txt`-файлы
непосредственно из `input_directory`, без рекурсии, и сортируем по имени. Пустой
каталог считается ошибкой. Имя без последнего расширения — ID: `network.txt` хранится в
`network/tree.json` и `network/progress.json`, ответ — `network/network_sol.txt`.
Старый список `inputs` также поддерживается, но его нельзя задавать одновременно
с `input_directory`; имена без расширения в списке должны быть уникальными.

`resume` принимает каталог. Исходные TXT обязательны. При переносе каталога можно
поменять пути к TXT, число работников, интервал сохранения и рабочий каталог ответов.
Имя каждого файла, содержимое его графа и alpha_step должны сохраняться.
Порядок файлов можно менять: checkpoint привязан к имени, а не к позиции в списке.
При добавлении нового TXT программа создаёт для него отдельное состояние.
Выбор графов для resume определяется текущим input_directory или inputs; каталоги
checkpoint для невыбранных файлов не обрабатываются. Предполагаем, что нужные
исходные TXT не удаляются и не изменяются пользователем.
Содержимое входа повторно не сверяется: используем тот же неизменённый TXT.
Контрольных сумм нет. Секреты из конфигурации не сохраняются.

Поддерживается только формат JSON версии 5 с диапазонами.
Прежние версии, одиночные курсоры и SQLite-checkpoint не поддерживаются. Новый `run` требует каталога без
существующих checkpoint-файлов. Для копирования checkpoint сначала остановите
процесс через SIGINT/SIGTERM: отдельные JSON атомарны, но копирование всего каталога
во время записи само по себе не является согласованным снимком. ZIP добавим отдельно.

## tree.json

Содержит версию формата, имя файла без расширения как ID графа, метаданные (имя входа,
alpha_step, версия алгоритма), состояние построения и само дерево:

```json
{
  "version": 5,
  "graph_id": "first",
  "metadata": {"input": "first.txt", "alpha_step": 0.1, "algorithm": "node-cursor-v1"},
  "state": {"minimum_size": 1, "next_parent": 1, "node_count": 3},
  "nodes": {"0": {"level": 1, "parent": 0, "set": 0}},
  "sets": {"0": [10, 20, 30]}
}
```

Пример показывает форму записи; полное дерево содержит все ноды до `node_count`.
`state=null` означает, что построение ещё не началось. Наборы вершин на разных
уровнях разделяют хранение через `set`. Рёбер исходного графа здесь нет.

Дети и `next_parent` публикуются под одним mutex после полного расширения родителя.
Прерванная обработка родителя, включая KVCC-ENUM/GLOBAL-CUT, повторяется целиком.
Построенное дерево обязательно сохраняется до запуска перебора и больше не меняется.

## progress.json

Содержит состояния нод для всех размеров r. Ключ ноды — `r/k/i`, где i — её
стабильный порядковый номер среди нод уровня k с размером не меньше r.

```json
{
  "version": 5,
  "graph_id": "first",
  "metadata": {"input": "first.txt", "alpha_step": 0.1, "algorithm": "node-cursor-v1"},
  "nodes": {
    "3/2/0": {
      "status": "IN_PROGRESS",
      "next_unassigned": "10",
      "unfinished_ranges": [{"begin": "0", "next": "2", "end": "10"}]
    },
    "3/2/1": {"status": "FINISHED_FOUND", "vertices": [70, 80, 90]},
    "4/2/0": {"status": "FINISHED_NOT_FOUND"}
  }
}
```

`next_unassigned` — начало ещё не выданной части перебора. Каждый незавершённый
диапазон хранит свой `next` — номер следующей непроверенной комбинации в
лексикографическом порядке. Все номера — десятичные BigInt в строках.
Начальный статус — `NOT_PROCESSED`. После неуспеха курсор продвигается;
прерывание во время проверки оставляет его на текущем подмножестве. Несколько
работников могут обрабатывать разные диапазоны одной ноды.
[Выдача диапазонов, инварианты и совместимость](parallel-ranges.md).

Отдельного сохранения результатов нет. После `resume` уровни просматриваются в
порядке убывания k: завершённые неуспешные ноды пропускаются, `FINISHED_FOUND`
возвращает сохранённые вершины, активные продолжаются с курсоров незавершённых диапазонов. Ответы k=0/1
получаем повторно простым обходом. Кеш по r существует только в оперативной памяти.
Файлы ответов снова формируются через атомарную замену; блоки alpha не дублируются.

## Надёжность

- Интервал `checkpoint_interval_seconds` по умолчанию 60 секунд. Найденный свидетель
  записывается немедленно. На каждом сохранении переписываются только изменённые
  документы, но каждый такой JSON — целиком.
- Запись: временный файл рядом, закрытие и fsync, атомарный rename, fsync каталога.
  Остаток временного файла после падения не читается как готовое состояние.
- Сначала сохраняется дерево, затем прогресс. Во время построения прогресс пуст.
  При падении между заменами новый tree совместим со старым пустым progress.
- Проверяются JSON, версия, параметры, имя графа, структура дерева и курсоры
  комбинаций. Сравнение содержимого файлов через хеши не выполняется.
- Один процесс владеет каталогом через flock на `.checkpoint.lock`. Канонизация
  пути учитывает симлинки корневого каталога; каталоги графов не должны быть симлинками.
- Внутри диапазона работник обновляет собственный курсор. Сохранение считывает
  локальные курсоры, не останавливая перебор целиком. Общая блокировка checkpoint
  остаётся на границах диапазонов, при регистрации состояния и записи JSON;
  подробности — в [описании диапазонов](parallel-ranges.md).
- SIGINT/SIGTERM выставляют флаг, затем обычный код дожидается работников и сохраняет
  состояние; код выхода 130. SIGKILL восстанавливается с последнего полного файла.
  Ошибка записи останавливает вычисления с диагностикой.

## Проверки

- Сканирование каталога: сортировка, только обычные .txt без рекурсии; пустой каталог
  и конфликт вариантов конфигурации. Добавление нового имени перед прежними файлами
  не меняет их ID при resume; имена с пробелами и символом ~ поддерживаются.
- Все стартовые курсоры C6 при r=3: правильное число оставшихся комбинаций.
- Завершённые ноды не запускаются повторно; частичное дерево восстанавливается.
- Найденный ответ возвращается из статуса ноды; готовое дерево не переписывается.
- Копия каталога, временный оборванный файл, окно между заменами tree/progress,
  несовместимые файлы, блокировка повторного процесса, ошибка диска и SIGINT.
- Отдельные процессы: первый граф завершён, SIGKILL во время второго, продолжение
  другим числом потоков, SIGTERM/SIGINT, восстановление удалённого файла ответа,
  отсутствие исходного TXT, изменение параметров, повреждённый JSON и неизвестная версия.
- SIGKILL во время построения дерева клики и завершение после resume.

Текущий формат с диапазонами: macOS и Ubuntu — 14/14 групп
CTest прошли, включая принудительные падения и восстановление обеих фаз.
На macOS проверки checkpoint, solver, parallel и CLI также прошли под ThreadSanitizer
без сообщений о гонках.

## Ubuntu 22.04+

```sh
sudo apt-get update
sudo apt-get install build-essential cmake libboost-dev nlohmann-json3-dev python3
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release
cmake --build build -j
ctest --test-dir build --output-on-failure
```

Python нужен только процессным тестам. Без тестов: `-DBUILD_TESTING=OFF`.
После этого этапа — пользовательское ревью. Длительные пользовательские расчёты не запускались.
