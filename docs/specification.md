# Техническое задание

## Задача

Для простого связного неориентированного графа G и размера r найти индуцированный
подграф на ровно r вершинах с максимально возможной вершинной связностью κ.
Результат — число κ и набор выбранных вершин, задающий подграф.

Основа — Algorithm 1 из статьи *Graph downsizing: a fast heuristic for querying closely
connected subgraphs*, DOI 10.1007/s10732-026-09585-6. Локальная статья:
`/Users/davoitenko/Downloads/s10732-026-09585-6.pdf`.
Сначала строится дерево всех максимальных **по включению** k-связных индуцированных
подграфов, затем уровни проверяются в порядке убывания k. `PDownsize` заменяется точным
перебором всех r-подмножеств с проверкой κ ≥ k потоками для каждой пары до первого
неуспеха. Первый успех на текущем уровне даёт оптимум; если уровни k ≥ 2 не дали
успеха, обходом выбирается связный подграф размера r. Для r=1 ответ κ=0.

Перечислитель первой версии простой и точный: итеративное удаление вершин степени <k,
разделитель размера <k, обработка всех компонент с возвращением разделителя,
дедупликация и устранение немаксимальных результатов.
Теперь до основного этапа 3 реализуется алгоритм Wen et al. из arXiv:1703.08668v1
отдельными шагами с ревью после каждого:
1. Внешняя схема KVCC-ENUM и OVERLAP-PARTITION; GLOBAL_CUT — заглушка с явной ошибкой.
   Тесты используют подстановки. Старая наивная реализация GLOBAL_CUT не используется.
2. GLOBAL_CUT: Algorithm 2, разреженный сертификат из k scan-first
   лесов по §4.2, сеть с единичными ёмкостями, LOC-CUT, обе фазы поиска разделителя.
   Подстановки сохраняются для тестов, обычный вызов использует реальный алгоритм.
3. GLOBAL-CUT* и SWEEP (Algorithms 3–4), neighbor/group sweep из §5.
   Прежний Algorithm 2 доступен для сравнения в тестах.

Внешняя схема следует Algorithm 1 (с. 4): k-core, компоненты связности, GLOBAL_CUT
для каждой компоненты, возврат k-связной компоненты либо обработка всех частей
OVERLAP-PARTITION. Стек допустим вместо рекурсии. Отдельная фильтрация немаксимальных
наборов не нужна при корректном контракте GLOBAL_CUT.

## Вход, α и ответ

- C++20, CMake и CTest, целевая ОС Ubuntu 22.04+. Целевой сервер: 32 ядра, 128 ГБ RAM.
- Граф хранится как список смежности на `std::map` с исходными знаковыми 64-битными ID.
- Каждый TXT содержит по два целочисленных ID на строке ребра. Пустые строки и полные
  строки комментариев `#`/`%` пропускаются. Повторные и обратные рёбра объединяются.
  Петли, неверные строки, пустые и несвязные графы отклоняются.
- `alpha_step` — число `double` в (0,1], по умолчанию 0.1. Сетка: step, 2×step, …,
  обязательно включая α=1. r=max(1,floor(α×|V|)). Используется простая арифметика
  double; точная десятичная арифметика и обработка редких пограничных случаев не требуются.
- Графы и α обрабатываются последовательно, повторяющиеся r используют общий расчёт.
  Дерево строится один раз, ноды меньше минимального запрошенного r не сохраняются.
- Для каждого входного graph.txt — один graph_sol.txt. Каждый блок начинается строкой
  `alpha r k m`, затем m строк всех рёбер индуцированного подграфа с исходными ID.
  Блоки следуют по возрастанию α, повторяющиеся r имеют отдельные блоки. Для r=1
  выбранная вершина сохраняется в checkpoint и выводится в консоль.
- Ноды содержат наборы вершин, исходный граф общий и неизменяемый; одинаковые наборы
  на разных уровнях разделяют хранение. Уровень k задаёт порог, а не точную κ ноды.
- Потоки: Dinic с расщеплением вершин, внутренние ёмкости 1, концы не ограничены,
  прямой путь между смежными концами учитывается один раз. Остановка потока при k.
  Уровни k≥r при решении пропускаются.

## Параллелизм и восстановление последующих этапов

- Общий пул, число потоков настраивается. Строго обрабатывается максимальный
  незавершённый уровень текущего r. Диапазоны комбинаций независимы; очередь ограничена,
  индексы и число комбинаций — целые произвольной точности. Успех отменяет остальные
  задачи текущего r. Пары одного подмножества проверяются последовательно.
- SQLite-checkpoint содержит граф, параметры, дерево, очередь построения и позицию
  поиска разделителя, расчёты по r и статусы NOT_PROCESSED, IN_PROGRESS, FINISHED_FOUND,
  FINISHED_NOT_FOUND. Для диапазона хранится следующая непроверенная комбинация,
  для успеха — свидетель. Повтор незавершённой проверки допустим, пропуски недопустимы.
- Согласованный checkpoint по умолчанию каждые 60 секунд, успех — немедленно.
  Транзакции/WAL и standalone snapshot через SQLite backup API. Ответы формируются
  из сохранённых результатов через временный файл и атомарную замену.
- SIGINT/SIGTERM сохраняют состояние и останавливают вычисления. Ошибка записи
  останавливает расчёт. Проверяются версия, целостность и параметры; число потоков
  и интервалы можно менять. Один checkpoint одновременно принадлежит одному процессу.
- Конфигурация задаёт входы, шаг, потоки, рабочий каталог, интервалы и GitHub URL,
  ветку и учётные данные. Секреты не входят в checkpoint, архивы, логи или исходники.
- CLI: `run --config FILE`, `resume --checkpoint FILE --config FILE`;
  восстановление из SQLite, ZIP или manifest частей ZIP.
- GitHub: фоновая загрузка в ветку runs каждые 300 секунд и в конце; отдельный каталог
  запуска. ZIP >50 MiB делится на части с manifest размеров, порядка и хешей.
  Сетевые ошибки не прерывают расчёт, загрузка повторяется с задержкой и при resume.
  Обычные коммиты без force-push. На текущих этапах публикации нет.

## Границы этапов и проверки

1. Каркас, CLI, конфигурация, граф, α/r, формат ответов.
2. Dinic, проверки связности, полный перечислитель и дерево.
3. Последовательный точный PDownsize, решение всех α и общий файл ответов.
4. Параллельные диапазоны и остановка по успеху.
5. SQLite, snapshot/resume обеих фаз и ZIP.
6. GitHub, восстановление архивов и эксплуатационные проверки.

Этапы 1–3 и шаги Wen реализованы. Текущий этап 4: общий пул потоков, ленивые
диапазоны комбинаций с индексами произвольной точности, строгий барьер между уровнями
и остановка по первому успеху. `combination_chunk_size` задаёт размер диапазона (256 по умолчанию).
Дерево пока строится последовательно. `run` использует заданное число работников;
`validate` и `tree` сохраняют прежнее поведение. `resume` и функциональность этапов 5–6
ещё не реализованы; GitHub для `run` должен быть выключен.

Каждый этап заканчивается пользовательским ревью. Между итерациями код дополнительно
проверяют независимые ревьюеры, которым передаются только задача, ТЗ и код.
Корректность ядра сверяется с независимым перебором удаляемых вершин на всех графах
до 5 вершин и случайных до 8. Полнота перечислителя и дерева проверяется отдельно,
включая клики, циклы, мосты, пересекающиеся компоненты и цикл плюс треугольник.
На последующих этапах проверяются все r, равенство оптимумов при разных числах потоков,
отсутствие пропусков, принудительные падения/resume, повреждённое состояние и сбои сети.
Длительные расчёты запускаются после ревью, скорость заранее не обещается.

Ревью направлено на существенные ошибки алгоритма и инфраструктуры. Незначительные
замечания передаются пользователю без автоматического исправления и усложнения кода.
